# Releasing

This is a checklist for a future release, not a claim that a build has passed it. Record the commit, environment, commands, failures and results for each release. Keep existing commits, tags and binaries unchanged.

## Prepare and verify

1. Review the intended diff and open bugs. Update the canonical docs for behavior/compatibility changes and write factual release notes.
2. Set the intended new version with `npm version X.Y.Z --no-git-tag-version`, updating `package.json` and `package-lock.json` without creating a tag. Do not reuse a published version.
3. On Windows with Node.js 24, run:

```powershell
npm ci
npm run check:docs
npm test
npm run build
npm run test:ui
npm run test:web-chat
npm run test:welcome
npm run dist:win
```

4. Launch both generated installer and portable builds in a disposable Windows profile/VM. Open a project; edit and reopen a document; install a bundled chart plugin and open a chart; open a project app. Check ASAR/esbuild behavior and that the expected files are packaged. Record which Windows versions were actually tested. Unit/development checks do not prove packaged behavior.
5. Check version labels, asset names, license/trademark notices, and the absence of credentials/private workspace data. Generate SHA-256 checksums for the release assets and publish them with the release; do not claim the current in-app updater verifies them. It currently checks size only.

## Commit, tag and publish

Use normal commits and a **new** tag only after review. Do not amend published history, move an existing tag, backdate commits or force-push. Keep release binaries in GitHub Releases, outside Git source control.

The [Windows build workflow](../.github/workflows/windows.yml) is **manual** (`workflow_dispatch`). Pushing a branch or tag alone does not trigger it. On a reviewed new tag, a maintainer can dispatch it explicitly:

```powershell
gh workflow run windows.yml --ref vX.Y.Z
```

A dispatch on a branch uploads build artifacts. A dispatch on a tag also runs its release-attachment step. Review the logs and actual asset contents before treating them as ready for users. Alternatively, upload locally tested assets with the GitHub release tools. Do not treat autogenerated commit summaries as verified release notes.

Builds are unsigned in the current configuration. Signing and Windows reputation checks need separate validation; a certificate alone does not guarantee the absence of SmartScreen warnings. Do not instruct users to bypass a warning without checking what they downloaded.
